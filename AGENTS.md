# AGENTS.md

## Purpose

Repository-wide instructions for coding agents.

DO NOT edit this file unless explicitly requested.

Keep this file limited to routing and hard repository guardrails. Do not duplicate product,
requirements, design, architecture, development, or contribution documentation here.

## Sources of Truth

Read the sources applicable to the affected behavior before changing it:

- [PRODUCT.md](./PRODUCT.md) — product purpose and durable product principles.
- [docs/requirements.md](./docs/requirements.md) — accepted user-visible requirements.
- [DESIGN.md](./DESIGN.md) — UI, interaction, responsive, motion, and accessibility rules.
- [docs/architecture.md](./docs/architecture.md) — ownership, boundaries, IPC, persistence,
  concurrency, frontend, and audio architecture.
- [README.md](./README.md) — setup and development commands.
- [CONTRIBUTING.md](./CONTRIBUTING.md) — Issue, branch, commit, PR, and merge workflow.

When changing repository instructions, prompts, agent workflow, or development tooling, also read
[PHILOSOPHY.md](./PHILOSOPHY.md).

The current GitHub Issue defines the scope and acceptance conditions of the change.

A task may change an existing source-of-truth contract only when it does so explicitly. Current code
and tests provide implementation and regression evidence; they do not silently override an
authoritative contract.

If authoritative sources conflict about the affected responsibility, STOP and report the conflict
instead of choosing, combining, or reinterpreting them.

## Repository Guardrails

DO NOT use `any` unless the type cannot reasonably be represented otherwise and the reason is
documented at the use site.

DO NOT manually edit:

- `src/bindings.ts`
- files under `src-tauri/gen/`

When a Rust Tauri command or IPC type changes:

1. edit the authoritative Rust definition;
2. run `pnpm bindings:generate`;
3. update affected consumers;
4. run `pnpm bindings:check`.

DO NOT weaken linting, type checking, tests, security, accessibility, or real-time-audio constraints
to make a change pass.

DO NOT introduce a compatibility layer, abstraction, fallback, migration, or persistent mechanism
without a current requirement or consumer that needs it.

## UI Work

For changes affecting UI, interaction, layout, responsive behavior, typography, motion, or
accessibility:

1. read [DESIGN.md](./DESIGN.md);
2. read the applicable frontend rules in [docs/architecture/frontend.md](./docs/architecture/frontend.md)
   and the routing summary in [docs/architecture.md](./docs/architecture.md);
3. use [.agents/skills/impeccable/SKILL.md](./.agents/skills/impeccable/SKILL.md) according to its
   current instructions.

Responsive final geometry is CSS-owned. JavaScript viewport observation is limited to semantic and
accessibility behavior; it must not determine Grid layout or Motion coordinates. Motion usage must follow
the frontend architecture contract and its approved owners.

DO NOT claim an Impeccable playbook was used unless it was actually read and applied.

## Testing and Completion

Protect changed behavior with automated tests when the repository has an automated boundary capable
of proving it.

DO NOT claim validation that was not actually performed.

Before reporting an implementation task complete, run:

`pnpm check`

If `pnpm check` fails, DO NOT report the implementation as complete.

If required validation cannot run because the environment is unavailable, report the exact command,
the unavailable dependency or environment, and what remains unverified.

Use `pwsh` for PowerShell commands.

## Git and GitHub

Git and GitHub writes require an explicit user request.

Use `git` for local repository and Git transport operations and the GitHub connector for supported
GitHub operations.

DO NOT use `gh`.

Follow [CONTRIBUTING.md](./CONTRIBUTING.md) for Issue, branch, commit, push, PR, and merge workflow.
