# 0011: Albums and Album Artists are listed from summary tables; names sort and search by stored folded keys

Albums and Album Artists are rows of their own tables (`albums`, `album_artists`), written inside the scan transaction that changes their tracks (`library/summary.rs`), instead of being aggregated from `track_source_metadata` on every page. Bulk changes (a folder removed, Missing tracks deleted, a relink, a migration) rebuild them in one pass.

- A page of either list is an index range plus one join for the cover. Year and count sorts are plain indexed columns. Only the first page of a list counts it.
- Every sortable name has a stored sort key and every track one search key, both folded (`library/text.rs`): NFKC, katakana to hiragana, lowercase, Latin accents dropped; a SortOrder tag replaces the name as the sort source. Sort, filter and the scroll index are all functions of these keys, so they cannot disagree. Changing the folding means a migration that recomputes them.
- An album is (Album Artist, title, Edition). The Edition is the folder, so two printings of the same title and artist stay apart; disc folders are folded into their parent so a multi-disc album stays one. Compilations are settled in the same transaction, which moves untagged tracks of a folder between their own artist and "Various Artists" as tracks arrive or leave.
- Alternative rejected: keep aggregating (`GROUP BY`) per page. It is simple but costs time proportional to the whole Library for every page of a year or count sort, and it needs the per-row cover lookups this removes.
- The scroll index is a `GROUP BY` on the first character of the sort key column, run when the list's filter or sort changes, not per page. A jump skips rows by `OFFSET` over the same index to find the keyset cursor, so it reads only the target region.
