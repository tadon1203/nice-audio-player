# Nice Audio Player UI/UX Review

Target: `src/App.tsx` and the application shell, library, queue, playback Dock, and settings surfaces it composes.

## Executive summary

The product has a coherent, distinctive foundation: quiet grayscale structure, art-led emphasis, a persistent three-region playback Dock, and a Queue that behaves as a responsive context pane rather than a generic modal. The recent shared icon-button treatment is a meaningful improvement: it is more restrained, aligned, and stateful without adding decorative noise.

The largest remaining UX risk is not visual polish. It is the recovery and discovery experience when the library, queue, or output service is unavailable. In that state, the same view presents several independent error messages, a retry, an empty-library message, and an onboarding action at once. Each message is individually truthful, but together they make the next useful action unclear. The interface needs one owner for recovery per affected workflow.

## What is working

1. **Clear visual language.** The restrained canvas/surface contrast, one editorial heading, and media-first pages match the product’s local-first listening intent. The system avoids the generic “music SaaS” look.
2. **Responsive composition is robust.** Main content is intentionally replaced by Queue at constrained widths, rather than squeezed alongside it. The Dock preserves all three functional regions and keeps the main transport control centered.
3. **Queue motion has a meaningful spatial model.** The side/context pane’s directional slide and reduced-motion fallback communicate entering and leaving a related context without shifting persistent controls.
4. **Playback controls are structurally accessible.** Important controls have labels, native range input semantics, busy/disabled states, focus treatment, and the queue button exposes expanded state and its controlled region.
5. **Queue row actions are keyboard-considered.** The menu moves focus into the menu, supports Escape, arrows, Home/End, and restores focus to its trigger.
6. **Critical destructive library action is explained.** Removing a library folder uses a confirmation dialog and explicitly says music files are not deleted.

## Findings

### P1 — Collapse competing failure states into one actionable recovery state

**Evidence:** With local services unavailable, Library simultaneously shows scan-status failure, album-query failure with `Retry`, “No indexed music yet,” and “Open Library settings.” Queue similarly reports synchronization failure but leaves controls and two empty-state messages visible.

**Why it matters:** A first-time listener and a listener recovering from a real failure cannot tell whether retrying, adding a folder, or waiting is the correct next step. “No indexed music yet” also reads like successful empty data even when the actual query failed.

**Recommendation:** Model view state with a visible precedence: `unavailable/error` > `loading` > `empty/onboarding` > `content`. For each precedence state, show one short explanation and one primary recovery action. Example: “Library is unavailable. Try again, or open Library settings.” Do not show the normal empty state until the query has succeeded. Queue should offer an explicit `Retry queue` action (or a disabled, clearly explained status) rather than a bare synchronization error.

### P1 — Give destructive Queue operations an immediate recovery path

**Evidence:** `Clear upcoming` is one click and queue-item removal is immediately applied from the overflow menu. The library’s more consequential removal correctly explains its effect; the transient queue does not.

**Why it matters:** Clearing or removing is easy to do accidentally during attentive listening, and rebuilding a deliberate sequence may take time.

**Recommendation:** Keep the action direct, but show a short non-blocking confirmation with `Undo` after clear/remove. Do not use a modal confirmation for ordinary queue maintenance; it is slower than the harm warrants.

### P2 — Make icon-only controls discoverable without reintroducing visual clutter

**Evidence:** Queue, shuffle, repeat, mute, and per-row actions have good accessible names but no visible hover/focus label. Their symbols are familiar to experienced listeners but ambiguous for first-time users—particularly the Queue icon, repeat-cycle state, and overflow menu.

**Why it matters:** ARIA makes controls usable by assistive technology; it does not make their meaning discoverable to a sighted new listener. The current restraint can remain while improving learnability.

**Recommendation:** Add concise delayed tooltips on pointer hover and immediate text labels for keyboard focus, e.g. “Open queue”, “Shuffle”, “Repeat all”, and “More actions”. For repeat, expose the current state in the tooltip and preserve the visual “1” marker. Keep the shared `.icon-button` itself unchanged.

### P2 — Separate empty playback from active playback more decisively

**Evidence:** When no audio is selected, the full Dock still displays artwork placeholder, transport, `0:00 / --:--`, seek rail, Queue, volume, and an output-device error in the same visual grammar as active playback.

**Why it matters:** It uses substantial visual attention for inert controls and makes the initial screen feel more like a failed player than a ready library. The disabled state is correct, but the information hierarchy is not yet calm.

**Recommendation:** Retain the Dock’s geometry to avoid layout shift, but reduce inactive transport/timeline contrast and replace the ambiguous `0:00 / --:--` pair with a single subdued “Choose a track to begin” status. Keep Queue and volume available where they remain useful.

### P2 — Tighten the Library control hierarchy at wide widths

**Evidence:** On wide library screens, the title/tabs sit far left while search is placed at the far right; when no content is available, the gap becomes conspicuous. In the populated reference view, the same split makes scanning from tabs to search require a long eye movement.

**Why it matters:** The negative space is intentional and on-brand, but the controls belong to one browsing task. The current placement makes the search look detached from the filter it refines.

**Recommendation:** Keep the large editorial “Library” heading, then place tabs and search in a single secondary control row with an intentional max width. This preserves the empty field while making the browse/search relationship immediately legible.

### P2 — Turn application-level failures into an actionable, persistent status model

**Evidence:** Playback/output errors are displayed at the lower edge of the Dock; library errors are inline; queue errors are inline. `ApplicationActivityIndicator` has polite live announcement support, but the user sees different recovery patterns in each surface.

**Why it matters:** A local-first desktop app earns trust by making state and recovery predictably local. Mixed placements make a device or backend failure feel incidental rather than owned.

**Recommendation:** Define a shared error pattern: affected surface gets a concise inline error plus its direct recovery action; global activity indicator only summarizes asynchronous/background activity. Ensure repeated failures do not duplicate a local error and a global notice without adding a new action.

### P3 — Add a compact keyboard-control reference and global transport shortcuts

**Evidence:** Queue-menu keyboard handling and focus restoration are strong, but there is no in-app shortcut reference or visible global playback shortcut model.

**Why it matters:** A Windows listener with a large personal collection benefits from fast keyboard control, and discoverability matters even more for a minimal UI.

**Recommendation:** Add a small “Keyboard shortcuts” entry under Settings or an accessible help surface. Start with Space play/pause (when appropriate), arrow/seek behavior only if conflict-safe, Queue toggle, and Escape to close transient context. Do not capture text-entry shortcuts while search has focus.

## Cognitive-load assessment

**Moderate.** Browsing a healthy library is calm and low-noise. Load becomes high in failure/empty conditions because the user must infer which of several messages is authoritative, and in the Dock/Queue because icon meaning must be remembered rather than recognized. Addressing the two P1 items should make this consistently low.

## Persona stress test

- **Jordan, first-time local-library listener:** Needs one clear first action: add a folder, then visible scan progress, then a truthful empty/content result. The current state can expose errors and onboarding together.
- **Alex, large-library power listener:** Benefits from the fast grid, stable Dock, Queue, and keyboard-ready menu, but lacks visible transport/Queue shortcuts and safe undo for rapid queue editing.
- **Riley, listener recovering from an unavailable device/service:** Sees the failure, but does not consistently receive a recovery action at the point of failure. This is the most important trust gap.

## Suggested order of work

1. Implement mutually exclusive library/queue error, loading, empty, and onboarding states with one recovery action per state.
2. Add Undo feedback for clear/remove queue operations.
3. Add focus/hover tooltips to the shared icon-button surface and a compact shortcuts reference.
4. Refine inactive Dock copy and the Library tabs/search control row.
